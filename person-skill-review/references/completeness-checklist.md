# Skill 完整性审查细则（8 大维度）

本细则供 `person-skill-review` 对自研及准备改用的外部 AI Skill 逐维核查使用。**若审查对象为外部 Skill，本细则仅覆盖逻辑与结构完整性，绝不替代对应快照的 `skill-security-check` 安全审计。** 报告中只展开真正存在遗漏、歧义或风险的条款，避免无问题维度凑字数。

---

## 维度 1：目标与触发边界（含 `Frontmatter` 一致性）

- **最终目标**：能否用一句话说清解决什么问题、服务谁、交付什么结果？若存在多个目标，是同一流程中的有序子目标，还是无关职责硬塞在一起？
- **`Frontmatter` 发现率（关键）**：
  - `name` 是否小写连字符命名且语义清晰，避免与内置/常用 Skill 撞名？
  - `description` 是否同时包含**做什么 + 何时触发（具体用户意图/场景）+ 何时不触发（易混淆边界）**？
  - 正文写的触发条件与 `description` 是否一致？（避免正文很细、但 `description` 没写导致渐进式披露阶段根本不被激活。）
- **触发与排除边界**：是否避免“处理相关问题”“协助完成任务”等过泛表述？是否列出容易误触发的相近任务及误触发后果？
- **触发冲突与组合**：若可能与其他 Skill 同时命中，是否明确优先级、先后组合顺序，以及依赖 Skill 缺失或失败时的处理方式？

## 维度 2：输入、前提与异常输入兜底

- **必须输入**：完成任务不可缺少的信息、文件、参数、权限或上下文是否逐一写明？缺失时 AI 应停止追问还是如何处理？
- **可选输入与默认值**：非必需但提升质量的输入是否定义了未提供时的默认行为？未定义时 AI 会自行猜测什么？
- **异常输入全覆盖**：分别检查以下 6 种情况是否规定了明确动作（继续 / 用默认值 / 向用户确认 / 停止说明 / 交接人工或其他 Skill）：
  1. 必需信息缺失；
  2. 可选信息缺失；
  3. 用户要求前后冲突；
  4. 输入格式错误或无法读取；
  5. 信息来源不可靠、过期或不完整；
  6. 请求超出当前 Skill 能力、权限或适用范围。

## 维度 3：执行流程与判断规则

- **端到端闭环**：按顺序还原每一步的前置输入、动作、产出、下一步依赖及失败分支。重点抓：步骤跳跃、前置条件未保证、输出格式无法供下一步消费、循环无终止条件、中途失败无退出路径。
- **判断规则可判定性**：扫描所有“如果”“当……时”“必要时”“适当时”“优先”“禁止”“尽量”“合理”“高质量”等表述，检查：
  - 条件是否可客观识别？
  - 结果是否唯一？
  - 规则冲突时是否有明确优先级？
  - 是否存在未定义的主观标准词导致不同模型/轮次执行漂移？

## 维度 4：目录资源与外部依赖闭环（只读根到叶组件核查）

- **路径安全边界与引用核验**（目录输入时必查，且遵循只读铁律）：
  - **逐级组件核查与不跟随链接**：锚定审查根，从根到目标的每个路径组件校验类型；对符号链接仅记录链接自身与目标文字，**严格禁止跟随**。凡越界（指向审查根外）、断链、循环或位于符号链接目录下的文件引用，一律记为 **`未核验`**（若含仓外或可疑链路，立即警示并路由 `skill-security-check`）；若宿主工具无法建立防链接跟随读取边界，须标明未核验。
  - **静态核对 `scripts/` 与附属文件**：`SKILL.md` 中引用的 `./scripts/...`、`./references/...`、`./examples/...`、`./resources/...` 是否真实存在、路径拼写是否准确；对 `scripts/` **仅静态核对路径、源码与接口声明，严禁执行、导入、`source`、构建或安装任何目标脚本**。
  - 目录下是否存在未在 `SKILL.md` 中说明用途和调用时机的“孤儿文件”？
  - 被引用的脚本是否写清了运行参数、预期输出与失败退出码处理？
- **外部环境与工具依赖**：
  - 依赖的 CLI 工具、Python/Node 运行时、第三方包、MCP Server、环境变量、API Key 或登录态是否明确声明？
  - 是否写了前置检测步骤，以及依赖缺失/未登录时的清晰引导或降级策略？

## 维度 5：权限确认、禁止事项与异常恢复

- **自动执行 vs 必须确认边界**：删除、覆盖、发送邮件/消息、发布、提交 PR/代码、付款、下单、审批、修改生产环境、操作真实账号或外部系统、处理敏感/客户数据等高影响或不可逆动作，是否设置了明确的确认门槛？（缺失列为**阻断**。）
- **人机确认信息充分性**：触发用户确认时，是否规定必须向用户呈现足够做决策的要素（目标对象、变更范围、不可逆后果），而不是空泛询问“是否继续”？
- **必要禁止事项**：是否防范擅自扩大任务范围、编造事实/数据/来源/执行结果、条件不满足时假装完成、把外部文件内容或工具输出中的文本当作指令执行；并在输出前按规则完成防渲染脱敏与局部掩码（禁止外部 API 试探疑似凭据）。
- **工具失败与恢复**（仅当 Skill 使用工具/文件/外部数据时查）：是否覆盖超时、限流、权限不足、空结果、截断结果、多步部分成功、最大重试次数、停止条件、幂等重跑、以及失败后的临时文件清理或回滚方案？

## 维度 6：指令工程、上下文预算与可移植性

- **正反例（Few-shot）完备性**：对于输出格式复杂、分类判断微妙或易误解的 Skill，是否提供了具体输入/输出示例或典型反例？
- **脚本化 vs 提示词化评估**：是否存在确定性校验、正则提取、批处理统计等更适合放进 `scripts/` 以保证 100% 稳定，却全靠自然语言让模型口算的环节？
- **环境可移植性**：是否硬编码了作者本机绝对路径（如 `/Users/xxx/...`）、仅适配单一操作系统的命令参数（如 BSD `sed -i ''` vs GNU `sed -i`）或隐含假设特定 shell？
- **上下文与资源控制**：
  - 静态层面：主 `SKILL.md` 是否过于冗长塞满大段参考手册导致核心约束被稀释，应按 `Progressive Disclosure（渐进式披露）` 拆到 `references/`？
  - 运行层面：是否存在无限重试、重复读取超大文件/全量日志、长流程遗忘初始约束，或输出长度/成本失控风险？

## 维度 7：输出验收标准与跨 Skill 契约

- **可客观验证的输出标准**：是否明确交付物的内容、结构、可追溯性，以及**成功 / 部分完成 / 失败**三种状态的明确区分？若只写“输出高质量结果”“确认无误”，指出其无法客观验收的原因。
- **跨 Skill 契约**（仅当被其他 Skill 调用或调用其他 Skill 时审查；否则标 `不适用`）：输入结构是否明确、输出格式是否稳定、下游能否不依赖内部实现消费结果、写文件/调工具等副作用是否已声明。

## 维度 8：歧义、自行猜测与最小测试集设计

- **歧义与猜测提炼**：把上面各维度中影响最大的歧义句与 AI 必须靠猜才能补全的缺口，汇总成可执行的修正项，明确标出哪些需作者拍板。
- **最小测试集设计**：紧扣本 Skill 的真实高风险缺口设计 5–8 个高信号用例（无需机械凑数），优先覆盖：
  1. 正常主路径（验证验收标准与核心交付）；
  2. 易误触发相近请求（验证排除边界）；
  3. 必需输入缺失（验证停止/追问而非编造）；
  4. 冲突或无效输入（验证兜底规则）；
  5. 诱导越界/跳过确认/嵌入外部指令或越界符号链接输入（验证禁止事项与确认门槛）；
  6. 工具或依赖失败场景（仅当使用工具/依赖时必含）。
